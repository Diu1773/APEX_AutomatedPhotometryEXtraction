# LC 스텝 번호 훑기 — 설명문에 남은 옛 번호

**상태: 미완. 다른 세션이 이어서 하면 된다.**
코드(파이프라인 인덱스·러너·저널·경로 헬퍼)는 2026-08-26 에 창과 맞췄다
(커밋 `7022817`). 이 문서는 **주석·독스트링·사용자에게 뜨는 문자열**에 남은
옛 번호를 훑기 위한 것이다. 동작에는 영향이 없고, 읽는 사람을 속인다.

| 번호 | 단계 | 폴더 | 창 파일 |
|---|---|---|---|
| 8 | 선택형 PSF 측광 | `cmd_psf/` | `cmd/step8_psf_photometry.py` |

**창 파일 이름 넷은 실제 번호보다 하나 낮다.** 파일 이름으로 짐작하지 말고 안의
`step_index=` 를 읽는다 (`step_index + 1` 이 화면 번호다).

옛 번호 → 지금 번호: **선별 8→9 · 라이트커브 9→10 · 디트렌드 10→11 · 주기 11→12.**

## 3. 함정 — 먼저 읽을 것

**(가) 날짜로는 못 가른다.** `git blame` 으로 갈라 보려다 틀렸다. 실측 반례 둘:

- `apex/analysis/light_curve/raw_lightcurve.py:172` — **2026-08-20** 에 쓴 줄인데
  선별을 「Step 8」이라 부른다(옛 번호). 8 월 헤드리스 작업이 파이프라인의
  옛 번호를 그대로 썼기 때문이다.
- `apex/analysis/light_curve/detrend_output_service.py:221` — **2026-05-01** 에
  쓴 줄인데 디트렌드를 「Step 11」이라 불러 **지금 기준으로 맞다**. LC 번호가
  11 → 10 → 11 로 두 번 움직였기 때문이다.

**(나) 키워드 자동 분류도 못 쓴다.** 문장에 든 낱말로 구성요소를 찍어 봤더니
정밀도가 6 할쯤이었다. 오판 예:

- `apex/gui/tools/variable_star.py:3745` 「Step 12 handoff」— **이미 맞는데**
  문장에 "light-curve" 가 있어서 10 으로 바꾸라고 나왔다.
- `apex/pipeline/steps/lc_period.py:9` 「unlike step 9」— 라이트커브를 가리키니
  10 인데, 파일이 주기라서 12 로 나왔다.
- `apex/analysis/light_curve/target_config.py:71` — 설정 키가
  `lightcurve.target_id` 라 "lightcurve" 가 잡혔지만 문장은 선별을 가리킨다.

**(다) 숫자가 스텝이 아니라 폴더 이름일 때가 있다.** `step9_selection/` 은
`lc_selection/` 의 옛 폴더 이름이고, `step_paths_lc.py` 의 `step8_selection_dir`
같은 함수 이름도 호환용으로 남긴 옛 이름이다. 이런 건 **바꾸면 안 된다.**

**(라) LC 파일 안에서도 CMD·공통 스텝을 가리킬 수 있다.** 스텝 7(강제측광)·
스텝 6(마스터 카탈로그)은 두 모드가 같고 안 바뀌었다.

## 4. 하는 법

한 줄씩, 이 순서로:

1. 그 문장이 **어느 구성요소**를 말하는지 찾는다 (선별 / 라이트커브 / 디트렌드 /
   주기 / PSF / 공통 스텝).
2. 위 1 절 표에서 그 구성요소의 **지금 번호**를 본다.
3. 문장의 숫자가 다르면 고친다. 같으면 **그대로 둔다.**
4. 확정이 안 되면 그 줄이 쓰인 함수가 무엇을 읽고 쓰는지 본다 — 파일 경로
   (`lc_selection/` 등)가 대개 답을 준다.

**끝난 뒤 확인**: 아래 목록을 다시 뽑아 판정이 남지 않았는지 본다.

```bash
.venv-deploy/Scripts/python.exe -X utf8 -m pytest tests/ -q
```

설명문만 고치는 작업이라 테스트는 전부 그대로 통과해야 한다. 통과 기준이 바뀌면
동작을 건드린 것이므로 되돌린다.
