## 1. 결함: 설정 파일의 값이 계산에 안 쓰였다

### 어떻게 생겼나

설정 로더가 **2 단**이다. ① `parameter_map.py` 가 `[sky] annulus_scale` 같은 점 표기
키를 평평한 이름으로 옮겨 `raw` 에 넣고, ② `parameters_cmd.py` 가 그중 필요한 것만
골라 `SimpleNamespace` 에 담아 코드에 넘긴다.

문제는 **② 에서 이름을 안 적으면 아무 일도 안 일어난다**는 것이다. 예외도, 경고도,
로그도 없다. 값은 `raw` 에 얌전히 앉아 있고 코드는 기본값을 쓴다.

설정 하나가 죽는 길이 셋이었다.

| | 무슨 일 | 증상 |
|---|---|---|
| **맵에 없음** | `parameter_map.py` 에 행이 없다 | 파일에 써도 `raw` 에도 없다 |
| **떨어짐** | 맵엔 있는데 생성자가 안 집는다 | `raw` 엔 있는데 `P` 에 없다 |
| **안 읽음** | `P` 엔 있는데 코드가 다른 이름을 본다 | 다 있는데 안 쓰인다 |

### 실제로 무엇이 죽어 있었나 (커밋 `0758089`)

- **기기 제원** — `gain`·`read_noise` 가 맵에 없었다. 이건 측광 오차의 분모다.
- **조리개 배수** — `phot_aperture_scale` 등 셋. 사용자가 세 번 지적했던 그것.
- **캐시 서명** — 파라미터를 바꿔도 캐시가 무효화되지 않는 자리.
- **보정 스위치** — 켜고 끄는 값이 코드에 안 닿았다.

### 어떻게 찾았나

한 번의 grep 이 아니라 **세 갈래를 각각 기계로** 훑었다.

```bash
python -m apex.config.config_audit <apex_config.json>
```

`dropped_settings()` 는 맵에는 있는데 `P` 에 없는 이름을, `unmapped_keys()` 는 파일에
있는데 맵에 없는 키를 낸다. 사람 눈이 아니라 실행이 판정한다.

### 어떻게 고쳤나 — 증상이 아니라 원인

네 건을 잇는 건 증상 처치였다. 원인은 **같은 설정이 네 군데에 적혀 있었던 것**이다.

    ① 키 맵 (정본)
    ② 생성자 kwargs 452 줄 (손으로 동기화)
    ③ 즉시 덮어써져 버려지던 사본 (CMD 295 행 · LC 264 행)
    ④ GUI 파라미터 창의 위젯 정의

그래서 선언을 **한 줄**로 합쳤다 — `(경로, 속성명, 형, 기본값[, UI])`.

```python
(('sky', 'annulus_scale'), 'fitsky_annulus_scale', 'float', 6.0),
```

`build_settings(raw, TOML_KEY_MAP)` 가 이 행들로 값을 만든다. **행을 안 쓰면 설정이
아예 존재하지 않고, 쓰면 저절로 도착한다.** 반만 추가되는 상태를 만들 수 없다.

- 커밋 `ae0dc13` · 순수 삭제 **1,006 줄**
- 형 변환은 기존 `_getf`/`_geti`/`_as_bool` 을 그대로 옮겨 담았다 (인식 못 하는 bool 은
  기본값이 아니라 False, `str(True)` 는 float 이 아니다 — 미묘한 차이까지 보존)

### 어떻게 검증했나

**실데이터 워크스페이스 51 개**에서 리팩토링 전후의 `P` 를 전부 덤프해 값끼리 비교했다.

    비교한 속성 35,751 개 · 차이 **0**

체크포인트마다 다시 돌렸고 매번 0 이었다. 회귀는
`tests/test_config_settings_reach_code.py` 가 지킨다 — 도착하지 않는 설정 목록을
못 박아서, 늘어나면 테스트가 깨진다.

## 2. 결함: 파라미터 창이 남의 설정을 덮어썼다 (커밋 `5c683c3`)

이게 이번에 나온 것 중 **유일하게 데이터를 망가뜨리던** 결함이다.

Step 3(하늘 미리보기) 창에서 Save 를 누르면, Step 7 이 쓰는 하늘 환형(annulus) 값이
**6.0 / 3.0 → 4.0 / 2.0 으로 조용히 바뀌었다.**

원인은 1 절과 같은 종류다 — 창이 **읽는 이름과 쓰는 이름이 달랐다**. 창은 자기
위젯 기본값을 자기 이름으로 저장했고, Step 7 은 다른 이름을 읽었다. 그래서 창을
한 번 열었다 저장하면 측광 조리개 바깥의 하늘 고리가 좁아졌다.

**고침**: 창이 쓰는 이름과 읽는 이름을 맞췄다. 그리고 근본 수리로, 창의 위젯을
손으로 정의하지 않고 **맵 행에서 생성**하게 했다(`specs_from_map`, 커밋 `0d59f0b`).
맵에 없는 이름으로는 위젯을 만들 수 없으므로, **저장 못 하는 위젯이 구조적으로
불가능**해진다.

전수 조사 결과 창 30 개 중 22 개가 저장 못 하는 설정을 갖고 있었고, 전부 이었다
(커밋 `dbe1549`·`1936cc9`). 나머지 8 개는 의도된 것이라 테스트에 못 박았다.

## 3. 헤드리스가 GUI 없이 돌게 (커밋 `2f1165e`·`a5710cd`·`17311c5`·`4220c4b`)

사용자: *"gui없이도 스크립트만으로 측광할수있어야 한다고 생각함"*.

### 문제

CMD Step 8(PSF 측광)·Step 10(영점)의 **계산이 GUI 모듈 안에 `QThread` 서브클래스로**
들어 있었다. PyQt5 는 선택 의존성이라, Qt 없는 설치에서 두 스텝은 `NOT_IMPLEMENTED` 를
반환하고 멈췄다. 즉 스크립트만으로는 CMD 측광이 **불가능**했다.

원고는 *"runs both as a PyQt5 desktop application and as a scriptable, headless
command-line pipeline"* 이라고 쓰고 있었고, 감사표는 이미 **"과장됨"** 으로 판정해
두고 있었다.

### 옮기기 전에 측정부터

두 워커는 **`QThread` 메서드를 하나도 쓰지 않았다.** Qt 는 기반 클래스와 신호
12 개(emit 38 회)뿐이고 계산부는 순수 파이썬이었다. 그래서 이동 비용이 낮았다.

    apex/analysis/worker_signals.py            Channel / ReportsProgress
    apex/analysis/cmd/zeropoint_runner.py      Step 10 계산 (약 2,900 줄)
    apex/analysis/cmd/psf_photometry_runner.py Step 8 계산 (약 5,700 줄)
    apex/analysis/header_target.py             Step 1 헬퍼 (Qt 안 쓰는데 gui/ 에 있었다)

계산부는 **자기 어휘로** 알리고(`on_progress.send(...)`), 창이 그것을 자기
`pyqtSignal` 에 구독시킨다. 그래서 창과 스크립트가 **같은 객체**를 돈다 — "둘이
일치한다"가 검증 대상이 아니라 동일성의 문제가 된다.

```python
assert Step6PSFWorker.run is PsfPhotometryRunner.run
```

이관이 본문을 안 바꿨음은 HEAD 와 문자 단위로 대조했다 — **함수·클래스 46 개 전부 동일.**

### 실행하다 잡은 결함 (커밋 `4220c4b`)

Qt 없는 첫 실행에서 Step 8 이 바로 죽었다.

    AttributeError: 'PsfPhotometryRunner' object has no attribute 'error'

계산부는 채널로 바꿨는데 **부르는 쪽 네 곳**이 `worker.error.connect(...)` 를 그대로
쓰고 있었다(파이프라인 1 · 헤드리스 스크립트 2, 게다가 스크립트들은 `QCoreApplication`
까지 세우고 있었다). **정적 검사로는 안 보였고 실제로 돌려서 나왔다.**

### 실측 — 진짜 기본 설치에서

`pip install -e .` (gui extra 없이), **PyQt5 미설치**. M13 15 프레임.

## 4. Step 8 의 잔차 5 개 — 통제 실험이 첫 판정을 뒤집었다

Step 8 은 처음에 저장본과 **정확히는** 안 맞았다. `mag_psf` 최대차 4.8e-05,
1e-6 등급을 넘는 측정이 22,305 개 중 **5 개(0.02 %)**.

### 첫 판정과 그 정정

처음엔 *"실행 간 잡음"* 이라고 적었다. **틀렸다.**

Qt 있는 원래 환경으로 같은 입력을 돌려 저장본과 비교했다.

| 비교 | mag 최대차 | 1e-6 초과 |
|---|---|---|
| 저장본 vs **Qt 있는** 실행 | **0.0e+00** | 0 / 22,305 |
| 저장본 vs Qt 없는 실행 | 4.8e-05 | 5 / 22,305 |

**파이프라인은 결정론적이다** — 같은 환경, 같은 입력이면 비트까지 같다. 차이는
실행마다 흔들리는 잡음이 아니라 **환경에 붙어 있었다.** 그리고 이관은 결백하다.

두 환경의 패키지 93 개 대 49 개를 전부 대조하니, 측광에 관계된 것 중 버전이 다른 건

이제 모든 실행이 남긴다: `apex`·python·platform 과 답을 바꿀 수 있는 패키지들

## 5. Step 12(이소크론)를 헤드리스로 (커밋 `41f7f4f`)

### 왜 미뤄져 있었나 — Qt 가 아니었다

적합 서비스는 애초에 Qt 를 안 썼다. 막고 있던 건 **답을 정하는 설정을 설정 파일에
쓸 수 없었다**는 것이다. 그리고 라이브러리 기본값은 **시끄럽게 실패하지 않는다** —
기본 0.2–6 Gyr 창은 구상성단에 닿지도 못하고, E(B−V) 사전값 없이는 산개성단이 바닥에
붙는다(둘 다 실측: `validation/psf_crossinstrument/REPORT_UB_DEGENERACY.md`).

그래서 설정을 config 행으로 만들고, **결정적 설정이 없으면 스텝이 실행을 거부**한다.
아무것도 안 나오는 배치가, 자신 있게 틀린 나이를 내는 배치보다 낫다.

### 그리고 파리티를 확인하다 결함이 나왔다

창과 헤드리스가 같은 `fit_cluster_isochrone` 를 부르는 건 확인했다. 그런데 **설정을
만드는 경로가 갈라져 있었다** — 창은 탐색 상자를 코드에 박아두고 있었다.

```python
mh_bounds=(-1.0, 0.5), dm_bounds=(5.0, 18.0), ecolor_bounds=(0.0, 1.0)
```

**M13 은 [M/H] ≈ −1.5 다. 이 상자에 안 들어간다.**

더 나쁜 건 그다음이다. 서비스는 [M/H] 사전값 주위로 상자를 **좁히기만** 한다
(`max(lo,·)` / `min(hi,·)`). 그래서 금속 결핍 사전값을 주면:

```
prior=(-1.56, 0.10)  →  상자 [-1.000, -1.360]   ← lo > hi, 뒤집힘
prior=(-2.00, 0.20)  →  상자 [-1.000, -1.600]   ← 뒤집힘
```

격자 마스크가 `(mh >= lo) & (mh <= hi)` 라 **아무것도 안 걸린다.** 증상은 "데이터가
나쁜가 보다"로 읽히지, "벽이 엉뚱한 데 있다"로 읽히지 않는다.

### 고침

1. 번역을 한 곳으로 — `apex/analysis/cmd/isochrone_config.py`. 창과 헤드리스가
   **같은 `build_fit_config`** 를 쓰고, 창은 자기 위젯이 소유한 것만
   `dataclasses.replace` 로 덮는다.
2. 기본 상자를 사실에 맞게 — `[M/H]` 하한 −1.0 → **−2.2**(M13 문헌값을 되찾은 실행이
   쓴 값), `E(colour)` 상한 0.5 → **1.0**(데스크톱이 늘 쓰던 값, 조용한 축소 방지).
3. **뒤집힌 상자를 MCMC 전에 잡는다** — `check_bounds()`. 헤드리스는 BLOCKED,
   창은 경고 후 중단.

### 실측 — 돈다, 그리고 저장본을 재현한다

M13, PyQt5 없는 설치, seed 20260815.

    Step 12 [isochrone] -> ok  isochrone fit converged
    별 500 개 · 회원 1012/1445 · 경고 없음

| | 나이 (Gyr) | [M/H] | (m−M) | E(B−V) |
|---|---|---|---|---|
| 헤드리스 (상자 일치) | **13.298** | **−1.548** | **13.941** | **0.0966** |
| 저장본 | 13.339 | −1.559 | 13.945 | 0.0969 |
| 차이 | −0.041 (0.3 %) | +0.011 | −0.004 | −0.0004 |
| *문헌 (Harris)* | *12~13* | *−1.53* | | |

**서로 다른 구현이 만난 것**이라 더 의미가 있다 — 저장본은 GUI 가 아니라
`validation/cmd_step12_realdata.py` 가 만들었고, 그건 `fit_cluster_isochrone` 을
거치지 않고 `IsochroneFitterV2` 를 직접 부르며 별 선택도 자기 방식(`rng.choice`)이다.
구현도 표본도 다른데 나이가 0.3 %, [M/H] 가 0.011 dex 안에서 만난다.

### 거기까지 오는 데 두 번 틀렸다

**첫 시도는 5 Gyr 어긋났다**(8.44 vs 13.34). 처음엔 *"체인 길이(2000 vs 6000)와
미수렴"* 이라고 적었다 — **틀렸다.** 32×6000 을 돌리니 32×2000 과 소수점 넷째 자리까지
같았고, R-hat 은 오히려 헤드리스가 3.02 로 저장본 9.03 보다 잘 섞였다. 서비스 코드
주석이 이미 그 성질을 적어두고 있었다: *"2,000 은 규칙을 못 통과하고 6,000 은
통과했지만 중앙값은 셋째 자리까지 일치했다."*

**진짜 원인은 탐색 상자였다.** `docs/validation_realdata.md` 에 저장본을 만든 명령이
그대로 있다.

    --age-bounds 9.9 10.15 --mh-bounds -1.8 -1.0 --dm-bounds 13.5 15.2 --ecolor-bounds 0.0 0.2

| | 저장본 | 내 첫 시도 |
|---|---|---|
| [M/H] | −1.8 ~ −1.0 | −2.2 ~ 0.5 |
| E(colour) | 0.0 ~ 0.2 | 0.0 ~ 1.0 |
| (m−M) | 13.5 ~ 15.2 | 5.0 ~ 18.0 |

내가 얻은 [M/H] = −2.10 은 **저장본의 상자 밖**이다. 문헌으로 좁힌 상자와 넓게 열어둔
상자가 축퇴된 사후분포의 서로 다른 최빈값에 앉은 것이고, 이 스텝 모듈의 독스트링이
처음부터 적어둔 말 그대로다 — *답을 정하는 건 어떤 색을, 얼마나 넓은 창에서,
어떤 사전값으로 맞추느냐다.*

> **교훈**: 넓은 상자는 구상성단을 담을 수 있게 해주는 대신 축퇴된 최빈값도 같이
> 열어준다. 오늘 기본 하한을 −2.2 로 넓힌 것은 "M13 을 담을 수 있게" 이지
> "M13 을 맞히게" 가 아니다. 성단별로 좁히는 건 이제 설정으로 할 수 있다.

> 첫 32×6000 시도는 40 분을 다 돌고 **결과를 쓰다가 죽었다** — 시작할 때 만든 빈
> 출력 폴더가 40 분 뒤엔 없었다(`FileNotFoundError`). 쓰기 직전에 폴더를 다시
> 만들도록 고쳤다. 긴 계산의 산출물이 폴더 하나 때문에 날아가면 안 된다.

### 덤으로 잡은 내 실수

내가 쓴 스텝이 요약에서 `converged` 키를 읽고 있었다. 서비스가 쓰는 이름은
`convergence_ok` 다. 없는 키는 None 이라 **수렴한 적합까지 전부 실패로 보고**했다.
자기 성공을 잘못 이름 붙이는 배치는 침묵하는 배치보다 나쁘다. 고치고 회귀 추가.

기록도 넓혔다 — 요약만이 아니라 **설정·별 개수·회원 판정·경고·입력 표 경로**까지
쓴다. 경계와 사전값 없이는 사후분포를 판단할 수 없다(벽에 붙은 중앙값은 측정이
아니라 벽이다).

## 6. 전체 스위트가 잡은 것 — 데스크톱 워커가 생성조차 안 됐다 (커밋 `64ae8f1`)

이 세션 내내 **표적 테스트만** 돌리고 있었다(머신 여유가 1 GB 대라 전체 스위트를
미뤘다). 다 고친 뒤 처음으로 끝까지 돌리니 1,191 개 중 1 개가 깨졌다.

    TypeError: ZeropointCalibrationRunner.__init__() missing 4 required
               positional arguments

**창에서 쓰는 워커를 만들 수가 없었다.** 헤드리스는 멀쩡했고 실제 Qt 없는 실행이
저장본을 0.0e+00 으로 재현했는데도, 창 쪽 생성 경로는 아무도 안 밟고 있었다.

원인은 다중상속 순서다. `class Worker(QThread, Runner)` 에서 sip 의 초기화가
**협조적 체인을 타고 내려가** 러너의 `__init__` 을 인자 없이 부른다. 네 가지를
실제로 만들어 돌려서 확인했다.

| 시도 | 결과 |
|---|---|
| `QThread` 먼저 초기화 (당시 코드) | 실패 |
| 러너 먼저 초기화 | 실패 |
| **기반 순서 뒤집기 `(Runner, QThread)`** | **OK** |
| `super(Runner, self).__init__()` | OK |

기반 순서를 뒤집으면 **조용한 쌍둥이도 같이 사라진다** — `QThread` 가 앞이면 자기
빈 `run` 이 계산을 가려서 `start()` 가 아무것도 안 하고 돌아온다. 그걸 막으려고
붙여 뒀던 `run = Runner.run` 명시 바인딩은 이제 MRO 가 해주므로 지웠다.

회귀(`tests/test_gui_workers_construct.py`)는 **생성 · 신호 전달 · `start()` 가
계산에 닿는지**를 확인한다. 공유 pytest 프로세스 안에서 QApplication 을 세우면
teardown 에서 Windows access violation 이 나는데, **같은 코드가 자기 프로세스에서는
깨끗이 끝난다**(둘 다 실측). 그래서 살아 있는 검사는 별도 인터프리터에서 돌린다 —
하네스 문제지 워커 문제가 아니다.

> **교훈**: 표적 테스트는 내가 바꾼 경로만 밟는다. 이관은 **밟지 않은 쪽**을 깨뜨린다.
