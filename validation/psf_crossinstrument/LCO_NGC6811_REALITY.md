# LCO NGC 6811 실사 — 성적표 최우선 계획의 전제가 틀렸다 (2026-08-11)

`APEX_ENGINE_SCORECARD.md` 는 **"우선순위는 이 하나가 압도적이다"** 로 LCO
NGC 6811 확보를 지목했고, 근거는 `lco_ngc6811_nights.txt` 의
**"U: count=96 / B: count=66 / V: count=94"** 였다. 실제로 받을 수 있는지
확인한 결과 **그 수치는 프레임 수가 아니었다.**

## 무엇이 틀렸나 — API 의 `count` 는 추정값이다

LCO 아카이브 API 응답에는 `count` 와 함께 `count_estimated: true` 가 온다.
필터별로 `count` 와 실제 페이징 결과를 나란히 재면:

| 질의 | API `count` | 실제 페이징 |
|---|---:|---:|
| FILTER=U | 58 | **0** |
| FILTER=B | 40 | 4 |
| FILTER=V | 56 | 4 |

`nights.txt` 의 96/66/94 는 이 추정값 계열이다. **NGC 6811 의 U 밴드는 LCO
아카이브에 한 장도 없다** — 공개분·비공개분·BANZAI 산출물 세 경로를 각각
전수 페이징해 모두 109 프레임으로 동일함을 확인했다.

부수 함정 하나: 아카이브의 표기는 **`NGC 6811`(공백 포함)** 이다. `NGC6811`
로 질의하면 `count` 는 그럴듯한 값을 돌려주지만 페이징 결과는 비어 있다.
`count` 만 보고 판단하면 여기서도 속는다.

## 실제로 있는 것

전수 조사 결과 공개 NGC 6811 프레임은 **109 장**, 두 밤뿐이다.

| 밤 | 기기 | 망원경 | 프레임 | 필터 |
|---|---|---|---:|---|
| 2016-12-13 | fs02 (Spectral) | 2m0a | 6 | B2 · V2 · R2 (이미 4 장 받아둠) |
| 2023-09-07 | **fa05 (Sinistro)** | **1m0a** (ELP) | **103** | **gp30 · rp30 · ip29 · zs14** |

용량·시간(프레임당 실측 10.1 MB, Range 요청으로 확인 — API 의 `filesize`
필드는 `None` 이라 쓸 수 없다):

| 산출물 | 프레임 | 용량 | 3 MB/s 기준 |
|---|---:|---:|---:|
| raw (RLEVEL 00) | 109 | 1.10 GB | ~6 분 |
| BANZAI (RLEVEL 91) | 109 | 4.23 GB | ~24 분 |
| **합계** | | **5.33 GB** | **~30 분** |

## 그래서 계획을 어떻게 바꾸는가

**잃은 것 — U 밴드 논거.** step12 의 g/r/i 축퇴(해가 사전분포에 지배됨)를
U 로 푼다는 경로는 NGC 6811 로는 불가능하다. 이 논거를 살리려면 다른 성단을
찾아야 한다 (`fetch_lco_clusters.py` 의 `m67_ubv` = M67/kb74/2015-04-01 세트가
후보이나 **미확인 — 확인 전에 논문 문장으로 쓰지 말 것**).

**얻은 것 — 오히려 더 강한 C 축 자료.** fa05 103 장은:

1. **두 번째 기기**다. 지금 Step 0 에만 있는 다기기 근거가 측광→CMD 사슬
   전체로 확장된다 (성적표 C 축의 유일한 ○ 가 사슬 전체로).
2. **APEX 가 이미 자기 카메라로 처리한 바로 그 성단**이다. "다른 데서도
   돈다"가 아니라 **같은 별을 두 기기로 측광해 직접 비교**가 된다 — 원래
   계획보다 강한 형태다.
3. **필터계가 SDSS 로 일치**한다(gp/rp/ip). APEX 의 M67 g/r/i 작업과 같은
   계라 영점·색항 논의가 그대로 이어진다.
4. **BANZAI 산출물이 같이 온다** — 독립 파이프라인 대조가 공짜다.
5. **5.33 GB · 30 분**이다. "용량·시간 견적 먼저"가 걸림돌이 아니었다.

**한 가지 확인 필요** — Step 0 을 돌리려면 그 밤의 bias/dark/flat 이 있어야
한다. BANZAI 프레임의 `related_frames` 로 따라갈 수 있으나 **아직 세지 않았다.**
보정 프레임이 공개돼 있지 않으면 APEX 는 BANZAI 산출물(RLEVEL 91)에서
Step 1 부터 시작해야 하고, 그러면 "raw→science 통합"이 아니라 "측광 사슬만"의
다기기 근거가 된다. 받기 전에 이것부터 확인할 것.

## 교훈

`count` 처럼 이름이 확정적으로 들리는 필드가 추정값인 경우가 있다.
**세어야 할 것은 세라** — 이 확인을 안 했으면 존재하지 않는 96 장의 U 밴드를
전제로 논문 계획을 세울 뻔했다.
