## 2. SYSREM vs PySysRem 핵심 루프 — 지배 성분 일치, 꼬리는 구현 의존

`sysrem_compare.py` → `sysrem_compare.json`. YZ Boo g 필터, 커버리지 ≥80 %
컷 후 241 별 × 124 프레임, 별별 중앙값 중심화(PySysRem 고유 관례)를 양쪽에
동일 적용. PySysRem 은 Python 2 잔재(`print >>`)로 import 불가라 **핵심 갱신
루프(sysrem.py 73–101 행)를 구조 그대로 옮겨** 썼다 — 비교 대상은 갱신식이다.

| 지표 | 10 iter (원본) | 50 iter |
|---|---:|---:|
| 성분 best-match \|corr\| | 0.890 / 0.729 / 0.584 / 0.074 / 0.132 | 0.903 / 0.728 / 0.579 / 0.073 / 0.127 |
| 밝은 셀(err<20 mmag, 5,095 개) Δ잔차 RMS | 14.9 mmag | 14.1 mmag |
| 전체 잔차 RMS (APEX / PySysRem) | 385.7 / 370.5 | 385.7 / 369.4 |

**판정** — 추세제거가 실제로 제거해야 할 **지배 계통성분은 두 구현이 같은 것을
찾는다**(\|corr\| 0.90). 2·3 번은 부분 일치, 4·5 번은 불일치. 이는 가중
저계수 근사의 **비유일성** 때문이다 — 약한 성분은 강도가 비슷해 반복 수축이
국소해에 앉고, 목적함수는 그 사이에서 무차별하다. Tamuz+2005 가 성분 수를
보수적으로 쓰라고 권한 이유와 정합.

**운용 함의** — APEX 기본 `n_iter=5` 중 4·5 번째 성분은 이 자료에서 제약이
약하다. 성분별 제거량을 보고하고 사용자에게 성분 수 선택 근거를 주는 것이
다음 개선 지점.

**프로토콜 함정 둘 (재현 시 주의)**:
1. **가중평균으로 사전 중심화하면 PySysRem 초기화가 퇴화한다** — 첫 c 갱신이
   정확히 그 가중평균이라 0 이 되고, 다음 a 갱신이 0/0→NaN. `nanmean` 이
   그것을 가려 "불일치"처럼 보였다(1 차 시도 comp1 corr 0.09). 별별
   **중앙값** 중심화가 맞다. APEX 의 프레임측 초기화는 어느 중심화에도
   안전하다 — 이 비대칭 자체가 감사 관찰이다.
2. 일치 판정은 **가중치가 있는 셀에서만** 의미가 있다 — 비가중 RMS 는 어두운
   별 잡음이 지배하고, 그 셀에서는 가중 문제가 해 사이에 무차별하다.
